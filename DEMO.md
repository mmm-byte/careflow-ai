# Demo Guide

> **DEMO · SYNTHETIC DATA · NOT FOR CLINICAL USE**

A 10-minute walkthrough of CareFlow AI. Written to be followed live.

---

## Before the demo

```bash
npm install
npm run dev
```

Open `http://localhost:3000`.

**Do this first.** The embedding model (~32 MB) downloads on first use. Open the app and run one
workflow _before_ the demo starts, so the weights are cached and the cold start does not eat your
clock. The Model Lab will show a cold-start figure if you want to point at it — but a live
cold-start during a demo is a distraction, not a feature.

### Browser setup

- Open the app in a **separate tab** from your notes, so the model worker keeps running.
- Resize the window to roughly 1440×900 for the desktop layout.
- If presenting on a projector, the design system's contrast holds, but the sidebar collapses below
  1024 px — mention the responsive behaviour rather than fighting it.

## The 10-minute run

### 1 · The banner (15 seconds)

Point at the persistent strip at the top of every screen.

> "Everything here is synthetic. There is no real patient data in this repository, and the page is
> marked no-index. This is a demonstration of the engineering, not a clinical tool."

### 2 · Dashboard (60 seconds)

The roster of seven synthetic residents, and the aggregate counts.

> "Every number on this screen is computed from the loaded dataset and the workflows you have run in
> this browser. Nothing is hard-coded. That is the property I want to show you before we look at
> anything else."

Open the **Model lab** briefly to show the model card, the ensemble design and the measured
comparison. Do not linger — it is the deep cut, and it is where questions go.

### 3 · Residents (60 seconds)

Pick a resident with an interesting record — one with both a wound note and a medication follow-up.

> "This is the normalised view: encounters, observations, documents, care-plan activities and
> appointments, merged into one timeline. Behind it is a 40-entry FHIR R4 bundle with real reference
> resolution."

Click through to the **FHIR explorer** and show one reference being resolved.

> "Every reference is resolved against the bundle. Directory resources like Organization and
> Practitioner are recognised and excluded from data-quality warnings — treating them as data
> problems was generating noise on every load."

### 4 · Run a workflow (90 seconds)

Go to **Residents**, select the resident, and press **Run workflow**. Then switch to **Execution**.

> "Eleven stages. Each one records its real measured duration — this is the orchestrator's actual
> timings, not a simulated timeline. Watch what happens."

Let it finish. It stops at `await-approval`.

> "It stops here. The orchestrator can reach a proposal, never an action. There is no code path that
> skips this stage."

### 5 · The inspector (90 seconds)

This is the most important screen. Show, in order:

1. **The input** — the exact normalised text the classifiers consumed.
2. **Each engine separately** — the rules engine's label and confidence, the model's label and
   confidence. They are not averaged into a single number you cannot interrogate.
3. **The matched phrases** — the rules engine naming every phrase it hit.
4. **The safety gates** — all eight, with their outcomes.
5. **The model metadata** — identifier, quantisation, dimensions, cold-start and warm latency.

> "This is the difference between a model that gives you an answer and a model that gives you an
> answer you can check. Every score here is inspectable, and the rules engine can name every phrase
> it matched."

### 6 · Approve (60 seconds)

Go to **Review and approval**. Edit the action text, then approve with a reason.

> "Every consequential step needs a human. You can approve, edit or reject, and the reason is
> recorded."

If the model was unavailable, the decision banner says so, and the fallback marker shows which
engine produced the answer. Mention it here rather than hiding it.

### 7 · The audit trail (60 seconds)

> "Your decision, the evidence behind it, and a synthetic FHIR Task artifact with the decision
> label, the confidence and the reviewer id in extensions. Tagged SYNTHETIC so it can never be
> mistaken for a real task downstream."

### 8 · Evaluation lab (90 seconds)

Press **Run evaluation** and let the metrics appear.

> "This is not a stored result. The Evaluation Lab runs the same code as the CLI — same scoring
> pipeline, same runner — so the numbers in the browser and the numbers in the README are the same
> numbers. The committed report at reports/evaluation.json is generated by that same code."

Point at the ensemble's coverage number being _lower_ than the rules engine's.

> "The ensemble commits less often than rules alone. That is the agreement gate doing its job: it
> trades coverage for certainty, and it eliminated every incorrect recommendation."

Then read the caveat aloud:

> "52 synthetic scenarios. '100% selective accuracy' means no wrong answers in 52 hand-written
> synthetic records. It is not a clinical performance claim, and the documentation says so in the
> same breath as the number."

### 9 · Observability (30 seconds)

> "Real telemetry from the workflows you have run in this browser. Stage durations, engine
> agreement, fallback count, abstention count. Stored locally, resettable."

### 10 · Architecture (60 seconds)

> "Implemented versus proposed, kept explicitly separate. The architecture view in the app and
> ARCHITECTURE.md both draw that line."

Close on the limitations, which are documented rather than buried:

> "No temporal reasoning, no bias analysis, a hand-curated vocabulary, `localStorage` is not an
> audit store, and none of the authentication or server-side controls a real deployment needs are
> implemented."

## The questions this demo is designed to provoke

If you have time, these are the ones worth steering towards.

### "Why not just use an LLM?"

> "Three labels over structured-ish nursing notes do not need one. The capability ceiling is not the
> binding constraint — privacy, latency, cost and determinism are. The model is a 32 MB embedding
> model running in a Web Worker, so no resident data leaves the device and the scores are
> deterministic enough to audit. If the task were 'summarise this note and draft a handover', the
> answer would be different."

### "How do you know the negation handling is right?"

> "The rules engine scopes negation to a clause, requires it within two words before the phrase,
> breaks scope at contrastive connectors, and lets a trailing negation reach back only one word —
> so 'pain not reported' is a denial but 'bleeding that did not stop' is not. The negated phrase is
> also masked out of the model's input, because an embedding model cannot tell the difference
> between 'chest pain' and 'no chest pain'. There are focused unit tests on each of those rules."

### "Your first model scored 10%. What happened?"

> "The scoring function, not the model. Raw cosine similarity differences between prototypes sat in
> such a narrow band that the argmax was numerical noise. Replacing raw similarity with a softmax
> over similarities at temperature 0.05 fixed it. The same model that scored 10% became competitive
> once the measurement was correct."

### "Why is the ensemble worse than either engine?"

> "It isn't — the _averaging_ ensemble was, at 76.2% selective accuracy against 100% and 95%
> individually. Averaging lets a confidently-wrong engine drag a correct one down, and lets partial
> agreement lift borderline records over the threshold. The shipped version gates on agreement
> instead: disagreement pins confidence to zero and routes to a human. That restored 100% on both
> suites, at the cost of 4 to 10 points of coverage."

### "What would make you stop trusting it?"

> "Coverage that drops so low the workflow is useless. A single incorrect recommendation in shadow
> deployment. Performance gaps between subgroups. Drift between the synthetic corpus and real
> documentation. Any of those would be a reason to stop and fix, not to lower the threshold."

### "How do you know it did not silently fall back?"

> "The original prototype did exactly that — it caught the model failure, fell back to rules, and
> the UI still said 'AI classification complete'. That was the worst bug in the first version. Now
> the fallback is a typed state, the decision records which engine produced it, the fallback rate
> is a computed metric, and a unit test asserts it."

### "What would you do next?"

> "Temporal reasoning first — detecting deterioration from the change in an observation rather than
> its absolute value is the highest-value missing capability. Then a real corpus with clinician
> annotation and inter-rater agreement, and a prospective shadow deployment measuring agreement
> with human judgement before anything influences a workflow."

## If the demo breaks

| Symptom                                    | What to do                                                                                                       |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| Model weights fail to download             | The rules engine still works. Say so — it demonstrates the fallback path honestly. Check `NODE_USE_ENV_PROXY=1`. |
| The browser is slow on first load          | The page is static; only the model weights are slow. Run one workflow ahead of time.                             |
| The evaluation takes too long              | Run `--suite=tuning` only, or use the Evaluation Lab with the rules engine selected.                             |
| The layout collapses on a narrow projector | Below 1024 px the sidebar becomes a horizontal strip. That is the responsive behaviour, not a bug.               |
| A workflow will not complete               | It is waiting at `await-approval` by design. Go to **Review and approval**.                                      |
