# CareFlow AI

**A care-operations copilot for senior-care workflows — FHIR R4 in, human-approved action out, all inference in the browser.**

> **DEMO · SYNTHETIC DATA · NOT FOR CLINICAL USE**
>
> Every resident, encounter, observation and document in this repository is generated by
> [`scripts/generate-dataset.ts`](scripts/generate-dataset.ts). There is no real patient data anywhere
> in the system, and none is ever transmitted to a server. This project is an engineering case study,
> not a medical device.

A nurse's shift does not fail because the data is missing. It fails because the data is spread across
encounters, observations, notes, appointments and care plans, and because deciding what deserves
attention _today_ requires reading all of them against each other. CareFlow AI demonstrates that
narrow workflow: assemble one resident's record from FHIR R4, normalise it, classify what needs
attention, propose an administrative action, and **stop for a human to approve it**.

The interesting engineering is not the interface. It is that:

- the classifier is a **small embedding model running in the browser** — no inference server, no PHI leaving the device;
- a **deterministic rules engine runs alongside it** as a genuinely separate system, not a fallback disguised as AI;
- the two must **independently agree** before anything is recommended;
- every metric in the repository is **computed from a live run**, never hard-coded;
- every consequential step **stops at a human approval gate** with an audit trail.

## The problem

Senior-care operations staff work from a fragmented record. A single resident's relevant history may
be spread over:

| Source              | What it contributes                       | What makes it hard                                   |
| ------------------- | ----------------------------------------- | ---------------------------------------------------- |
| `Encounter`         | When and why the resident was seen        | Narrative text, free-form and inconsistent           |
| `Observation`       | Structured vitals and measurements        | Often out of range, but the note may say "ruled out" |
| `DocumentReference` | Nursing notes, handover, incident reports | The highest-signal content and the messiest          |
| `Appointment`       | Scheduled and missed follow-up            | Admin text with little clinical content              |
| `CarePlan`          | Open goals and activities                 | Long, partly-completed, often administrative         |
| `Task`              | Outstanding work items                    | Direct evidence of open loops                        |

Reading all of that and deciding "does this person need attention today?" is a multi-minute task that
happens dozens of times a shift, and getting it wrong in either direction is expensive: miss an
acute change, or send a stable resident to the top of the list for no reason.

The hard part is not the read. It is the _judgement_ — knowing whether a phrase is a genuine safety
signal or a denial ("chest pain ruled out"), whether an out-of-range number is new, and whether the
text is even about this resident's care.

## What it does

The complete implemented workflow, in order:

```
Load resident ─▶ Validate FHIR ─▶ Retrieve encounter
                                      │
                                      ▼
                                Retrieve observations
                                      │
                                      ▼
                                Process document
                                      │
                                      ▼
                                  Classify ◀── rules engine + embedding model
                                      │              (must agree)
                                      ▼
                               Check care plan
                                      │
                                      ▼
                            Prepare proposed action
                                      │
                                      ▼
                                Validate output
                                      │
                                      ▼
                              ⛔ AWAIT APPROVAL ⛔
                                      │
                          ┌───────────┴───────────┐
                          ▼                       ▼
                      Approved                 Rejected
```

Three labels, and only three. They describe **operational attention**, never clinical severity:

| Label       | Meaning                                                   | Proposed action                                                |
| ----------- | --------------------------------------------------------- | -------------------------------------------------------------- |
| `priority`  | A safety-relevant signal suggests prompt clinician review | Route to a clinician for priority review within the same shift |
| `follow-up` | Administrative or monitoring work is outstanding          | Create a follow-up task for the care team                      |
| `routine`   | No escalation indicated; normal cadence                   | Record no workflow action                                      |

The model never diagnoses, never suggests a treatment, never selects medication or a dose, and
never writes to any clinical system. The only thing it produces is a classification and a proposed
administrative action, and that action is inert until a human approves it.

## Demo walkthrough

**Requires:** Node.js 20+ and a modern browser. The model weights (~32 MB) are fetched from the
Hugging Face CDN on first load and cached by the browser.

```bash
npm install
npm run dev          # http://localhost:3000
```

Then, in the browser:

1. **Dashboard** — resident roster, aggregate workflow counts computed from your own runs.
2. **Residents** — pick a synthetic resident; see their timeline, observations and care-plan work.
3. **Execution** — press **Run workflow**. Watch the eleven stages execute with real durations.
4. **Inspector** — the full evidence trail: scores, matched phrases, safety gates, model metadata.
   Every evidence row links to the FHIR resource it came from, so a reviewer can check the source.
5. **Review** — approve, edit or reject the proposal. Nothing has happened until you do.
6. **Audit trail** — your decision, its evidence, and the synthetic FHIR `Task` artifact it produced.

Five additional sections cover **FHIR explorer**, **Evaluation lab**, **Model lab**,
**Observability** and **Architecture**.

## The AI approach

The classifier is **not** a large language model, and it is not asked to reason about clinical text.
It is a small sentence embedding model that maps a record to a vector, compares that vector against
a set of labelled prototypes, and produces calibrated scores for three workflow labels.

The pipeline is deliberately split so each engine sees the text it can handle best:

```
raw record
   │
   ├──▶ repair encoding, strip formatting noise
   │       │
   │       ├──▶ rules engine   ── exact phrase matching, negation scoping
   │       │                        (reads repaired ORIGINAL wording, so it can
   │       │                         quote exact phrases back to the reviewer)
   │       │
   │       └──▶ expand abbreviations, mask negated phrases
   │               │
   │               └──▶ embedding model ── sentence segmentation,
   │                                     prototype max-similarity
   │
   └──▶ both must independently select the same label
           │
           └──▶ disagreement ⇒ confidence pinned to 0 ⇒ manual review
```

### The rules engine is not AI, and is never called AI

The deterministic engine matches phrases and regular expressions against curated clinical and
administrative vocabularies. It is fully explainable — it can name every phrase it matched — and
it runs in under a millisecond.

Its most important behaviour is **negation handling**, because naive keyword matching gets this
wrong in the dangerous direction. "Chest pain ruled out" contains "chest pain". The rules engine
scopes negation to a clause, requires it to be within two words of the phrase, and handles
contrastive connectors ("no fever, **but** chest pain present") by breaking the scope at the
connector. A negated trigger phrase is removed from the model input too, so an embedding model does
not read a denial as a symptom.

### The model is small on purpose

`Xenova/bge-small-en-v1.5`, quantized to `q8`, run through
[`@huggingface/transformers`](https://github.com/huggingface/transformers.js) in a Web Worker.
~32 MB downloaded, ~384 dimensions, and it runs entirely on the user's device.

Three labels with three prototype sentences each do not need a 7-billion-parameter model. They need
a good sentence encoder and careful threshold calibration. See
[MODEL_CARD.md](MODEL_CARD.md) for the full card.

### The ensemble requires agreement

This is the design decision most worth discussing, and it was **reached by measurement, not taste**.

The conventional approach — average the two engines' confidences and hope they compensate — was
implemented first and measured. It performed **worse than either engine alone**: 76.2% selective
accuracy against 100% and 95% individually. One confidently-wrong engine drags a correct one down,
and borderline records clear the threshold that neither engine should have cleared.

The shipped design instead **gates on agreement**:

- both engines independently select the same label **and** each clears the confidence threshold → committed;
- either engine abstains, or they select different labels → fused confidence is pinned to **0**, the workflow routes to manual review.

This restores 100% selective accuracy on both suites at the cost of coverage. That trade is
explicit and measured, not hidden. See [MODEL_CARD.md](MODEL_CARD.md#ensemble-design) and
[EVALUATION.md](EVALUATION.md).

### Eight safety gates

Before a proposal can reach the reviewer, eight checks run. Any failure forces manual review:

| Gate               | What it catches                                      |
| ------------------ | ---------------------------------------------------- |
| `input-present`    | Empty or whitespace-only input                       |
| `content-depth`    | Too few words to classify meaningfully (minimum 6)   |
| `domain-relevance` | Text that is not about care at all                   |
| `fhir-validity`    | Validation errors in the underlying resources        |
| `label-separation` | One label dominates the others too strongly to trust |
| `contradiction`    | Mutually exclusive signals in the same record        |
| `clinical-scope`   | Text implying diagnosis or treatment requests        |
| `engine-agreement` | The two engines disagree, or one abstained           |

The `domain-relevance` gate is two-tier: strong care vocabulary (wound, medication, audiometry…)
is sufficient alone, while weak administrative vocabulary (appointment, schedule, monitoring) only
counts when a concrete clinical detail is also present. "The fire drill is scheduled for Tuesday"
therefore routes to manual review rather than being classified.

## Why small models

| Property           | Small browser model                       | Large server model               |
| ------------------ | ----------------------------------------- | -------------------------------- |
| PHI exposure       | Stays on device                           | Leaves the browser               |
| Network dependency | One-time model download                   | Every inference call             |
| Latency            | ~30 ms warm, in a worker                  | Network round-trip plus queueing |
| Operational cost   | Effectively zero                          | Scales with usage                |
| Auditability       | Deterministic scores, inspectable weights | Opaque, prompt-dependent         |
| Capability ceiling | Strong within a narrow label space        | Unnecessary for 3 labels         |

For three workflow labels over structured-ish nursing notes, the capability ceiling is not the
binding constraint. Data privacy, latency, cost and determinism are.

## Model selection was measured, not assumed

The first candidate was `Xenova/all-MiniLM-L6-v2` (21.9 MB, int8). It scored **10% accuracy with
90% abstention** — barely usable.

The cause was not the model. It was the scoring function: raw cosine similarity differences between
prototypes sat in such a narrow band that the decision was dominated by numerical noise. Replacing
raw similarity with a **softmax over similarities** at temperature `0.05`, and scoring against
**multiple prototypes per label** with max-pooling, fixed it.

With the scoring fixed, both candidates were re-measured on the same suite:

| Candidate           | Size (int8/q8) | Selective accuracy | Coverage |
| ------------------- | -------------- | ------------------ | -------- |
| `all-MiniLM-L6-v2`  | 21.9 MB        | 88.9%              | —        |
| `bge-small-en-v1.5` | 32.2 MB        | **100%**           | —        |

`bge-small-en-v1.5` won on accuracy and was adopted despite being 10 MB larger. A threshold sweep
then selected `DECISION_THRESHOLD = 0.75` as the operating point with zero incorrect
recommendations.

## FHIR support

The parser handles the resource types the synthetic dataset exercises, with real R4 semantics:

- `Patient`, `Encounter`, `Observation`, `DocumentReference`, `Appointment`, `CarePlan`, `Task`
- directory resources (`Organization`, `Practitioner`) are recognised and excluded from data-quality warnings
- `Provenance` is detected and the synthetic-data marker is surfaced in the UI
- references are resolved against the bundle and unresolved references are reported
- patient extraction follows both `Encounter.subject` **and** `Encounter.participant.actor` — the latter is what real R4 encounter bundles use, and missing it was a real bug caught by dataset generation
- observations are normalised by code, unit, reference range and interpretation flag

The synthetic bundle contains **40 entries across 7 residents and 10 resource types**, and generates
with **0 warnings and 0 orphaned references**. See [ARCHITECTURE.md](ARCHITECTURE.md#fhir-layer).

## Evaluation methodology

Two suites, deliberately kept separate:

| Suite          | Scenarios | Role                                                                 |
| -------------- | --------- | -------------------------------------------------------------------- |
| **Tuning**     | 30        | Used while designing and calibrating the system                      |
| **Validation** | 22        | Written **after** the architecture was frozen, never used for tuning |

The validation suite exists to answer one question honestly: does this generalise, or did it just
memorise? It was written after the architecture was fixed and was never consulted while tuning
thresholds, vocabularies or prototypes. It exposed a genuinely narrow rules vocabulary, which was
then widened — a real finding, recorded rather than hidden.

Each scenario specifies the expected label and whether the system **should abstain**. Metrics are
computed from a live run in [`src/lib/eval/metrics.ts`](src/lib/eval/metrics.ts):

- **selective accuracy** — accuracy on records the system committed to (the safety-critical number)
- **coverage** — fraction of records committed to (the cost of being cautious)
- **macro F1** — per-label F1 averaged across all three labels
- **abstention rate** — fraction routed to manual review
- **fallback rate** — fraction where the model failed and the rules engine answered
- **per-class precision / recall / F1**, a confusion matrix, and per-scenario failure analysis

### Reproduce it

```bash
npm run evaluate                       # both suites, all three engines
npm run evaluate -- --suite=validation # one suite
npm run evaluate -- --engine=ensemble  # one engine
npm run evaluate -- --json             # machine-readable output
npm run evaluate:check                 # compare a fresh run against the committed report
```

The run writes [`reports/evaluation.json`](reports/evaluation.json), which is committed so every
number quoted in this repository is verifiable.

CI runs the same evaluation on every push and fails when the **behaviour** changes: a record
that committed a different label, or that committed instead of routing to manual review. The
comparison ignores wall-clock fields (timestamps, latency), because they change on every run and
a plain file diff would always report a difference.

It also accounts for the fact that the embedding model is quantized (`q8`) and quantized inference
is not bit-identical across CPUs. A GitHub x86-64 runner and an Apple-silicon laptop produce
slightly different embeddings for the same text, which can flip a record whose confidence sits
close to the decision threshold. An outcome difference within `0.12` of the threshold is
therefore reported but does not fail the gate; a difference away from the threshold does. The
margin was measured against a real cross-platform run, not guessed.

## Measured results

From `npm run evaluate` on the committed dataset, with the model at `q8`:

**Tuning suite (30 scenarios)**

| Engine                         | Committed | Incorrect | Selective accuracy | Macro F1 | Coverage | Median latency |
| ------------------------------ | --------: | --------: | -----------------: | -------: | -------: | -------------: |
| Rules only                     |        21 |     **0** |           **100%** |   0.8224 |    70.0% |           0 ms |
| Embedding model only           |        20 |     **1** |              95.0% |   0.7623 |    66.7% |          30 ms |
| **Ensemble (agreement-gated)** |        18 |     **0** |           **100%** |   0.7547 |    60.0% |          30 ms |

**Validation suite (22 scenarios, held out)**

| Engine                         | Committed | Incorrect | Selective accuracy | Macro F1 | Coverage | Median latency |
| ------------------------------ | --------: | --------: | -----------------: | -------: | -------: | -------------: |
| Rules only                     |        18 |     **0** |           **100%** |   0.8868 |    81.8% |           0 ms |
| Embedding model only           |        14 |     **0** |           **100%** |   0.7379 |    63.6% |          31 ms |
| **Ensemble (agreement-gated)** |        17 |     **0** |           **100%** |   0.8614 |    77.3% |          31 ms |

**Read this honestly.** The headline is _zero incorrect recommendations_ on both suites for the
shipped ensemble. The caveat is equally important: **52 scenarios is a small corpus**, the
distribution is synthetic and hand-written, and every scenario is a single resident record with
nowhere near the messiness of real free-text documentation. 100% selective accuracy here means
_"no wrong answers in 52 synthetic scenarios"_ — it does **not** mean the system is safe for real
clinical text. That limit is stated in [EVALUATION.md](EVALUATION.md#what-these-numbers-do-not-say)
and [SAFETY.md](SAFETY.md).

The ensemble's lower coverage on the tuning suite (60% vs 70% for rules alone) is the direct cost
of the agreement gate. It is a deliberate trade: fewer automated recommendations, zero incorrect
ones.

## Safety and privacy boundaries

**What this system will never do:**

- diagnose, or suggest a diagnosis
- recommend, alter, or select medication or a dose
- suggest a treatment or clinical intervention
- take any action in a clinical system
- transmit resident data to a server
- commit a recommendation without a human reviewer

**What leaves the browser:** the model weights, once. Nothing else. Resident data is processed
entirely client-side; the FHIR bundle is a static asset in `public/`, and the only network request
after the model has loaded is for model weights from the Hugging Face CDN.

**What is stored locally:** observability events and audit entries in `localStorage`, under
versioned keys (`careflow.observability.v1`, `careflow.audit.v1`), both resettable from the UI and
both containing synthetic data only.

A persistent **"DEMO · SYNTHETIC DATA · NOT FOR CLINICAL USE"** banner is displayed on every screen
and in the page metadata. No HIPAA compliance is claimed anywhere in this repository, and
[SAFETY.md](SAFETY.md) sets out precisely which controls would be required before any real use.

## Human in the loop

The orchestrator can reach a **proposal**, never an action.

`await-approval` is a hard barrier in the state machine. The workflow cannot advance past it
without a `ReviewDecision`. A reviewer can:

- **approve** — accept the proposed action as-is;
- **edit** — accept it with a different label or an edited action;
- **reject** — decline it.

Each outcome writes an audit entry containing the decision, the reviewer, the timestamp, the full
evidence snapshot (scores, safety checks, model metadata, source resource ids) and the resulting
synthetic FHIR R4 `Task` artifact with `SYNTHETIC` tags and `careflow-*` extensions.

A test asserts the barrier holds: _a workflow cannot leave the approval gate without a review_.

## Observability

Every workflow run emits per-stage events with real measured durations — not simulated. Events are
persisted to `localStorage` (capped at 200 entries) and aggregated into a live summary: stage
durations, engine agreement rates, fallback counts, abstention counts.

The Observability view shows the real telemetry from the workflows run in this browser, with a
one-click reset.

## Failure handling

Failure modes are designed for, not hoped away:

| Failure                                    | Behaviour                                                                                                               |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| Model fails to load (offline, blocked CDN) | Rules engine answers alone; the UI states that the model was unavailable rather than implying AI ran                    |
| Model throws during inference              | Caught, recorded as a fallback event, rules engine answers, **the UI says which engine actually produced the decision** |
| Low confidence                             | Routed to manual review with the reason                                                                                 |
| Engines disagree                           | Confidence pinned to 0, routed to manual review                                                                         |
| Malformed FHIR                             | Validation errors recorded; workflow blocked before classification                                                      |
| Out-of-domain text                         | `domain-relevance` gate fails, routed to manual review                                                                  |
| Contradictory signals                      | `contradiction` gate fails, routed to manual review                                                                     |
| Empty dataset                              | Explicit error state; the rest of the application remains usable                                                        |

An early version silently fell back to the rules engine while the UI still claimed an AI decision.
That was the single worst bug in the original prototype, and it is why the fallback path is now
explicitly labelled everywhere it can appear.

### Deploying to Vercel

The repository is ready to deploy: import it into Vercel and it builds as-is.

| Setting          | Value                   |
| ---------------- | ----------------------- |
| Framework        | Next.js (auto-detected) |
| Build command    | `npm run build`         |
| Output directory | `out`                   |
| Install command  | `npm ci`                |

`vercel.json` pins those settings and adds long-lived caching for hashed assets plus a small set of
security headers. There is nothing else to configure — no environment variables, no API keys, no
database.

Two things to know about the deployed build:

- **The model weights still come from the Hugging Face CDN** on first load. Vercel does not host
  them; the browser fetches and caches them. That is what keeps the deployment free and the
  resident data on the device.
- **The build is a static export**, so the deployment is a CDN of files. There is no server
  runtime, which means no cold starts and no server cost.

The repository also carries an `.npmrc` that sets `onnxruntime-node-install-cuda=skip`. The
`onnxruntime-node` package downloads optional CUDA execution-provider binaries on Linux x64, and
the upstream URL for the pinned version returns `404`, which breaks `npm ci` on every Linux x64
machine — including Vercel's build containers and GitHub Actions runners. The CPU binaries are
bundled inside the package and this project never uses CUDA, so skipping the download is correct
and keeps the install reproducible. `vercel.json` sets the same thing as a build environment
variable, which is the form that does not depend on npm's handling of unknown project config
keys.

## Trade-offs

**Two engines instead of one.** More code, more latency coordination, more to explain. Bought:
a genuinely independent second opinion and a measurable guarantee that a single confident error
cannot become a recommendation.

**Agreements over averaging.** Lower coverage (60% vs 70% on the tuning suite) and more manual
review. Bought: 100% selective accuracy on both suites instead of 76.2%.

**Embedding model instead of a language model.** Loses free-text reasoning and explanation quality.
Bought: deterministic scores, no inference server, ~30 ms latency, and auditability.

**Client-side only.** Loses shared model caching, server-side batch evaluation and central
monitoring. Bought: a static export with no backend at all, and PHI that cannot leave the device.

**A static export with no server.** Loses multi-user audit trails and a central trust boundary.
Bought: a project that runs from `file://` or any static host, with nothing to attack.

**Hand-written synthetic data.** Loses the realism of messy production data. Bought: a stable,
reviewable fixture with zero licensing or privacy concerns.

## Known limitations

These are real and not addressed by the work above:

1. **The evaluation corpus is small and synthetic.** 52 scenarios, hand-written, single-record.
   It cannot represent the long tail of real documentation. The 100% selective accuracy figure
   should not be read as a clinical performance claim.
2. **Three labels is a narrow output space.** The system answers "what deserves operational
   attention", not "what is wrong with this resident".
3. **The prototype set is tiny.** Three prototype sentences per label. There is no retrieval corpus,
   no few-shot prompting, and no learned calibration beyond a temperature and a threshold.
4. **No temporal reasoning.** The classifier reads one assembled record. It does not compare a
   value against its previous value, which is exactly what makes deterioration detectable.
5. **The rules vocabulary is English-only and manually curated.** It will miss clinical phrasing it
   has not seen. The `domain-relevance` gate is the backstop, not a substitute.
6. **No authentication, no multi-user audit.** The audit trail is per-browser `localStorage`.
7. **Model weights require network access on first load.** Fully offline operation is not supported.
8. **`localStorage` is not an audit store.** It is a demonstration of the audit _shape_. A real
   deployment needs an append-only, tamper-evident store.
9. **No performance testing at scale.** The 52-scenario suite runs in seconds; there is no load
   test, no concurrency analysis and no memory profiling.
10. **Not a medical device and not validated.** No regulatory review, no clinical validation, no
    safety case suitable for real deployment.

## Production roadmap

What this prototype would need before it could be considered for a real deployment — none of it is
implemented:

- **Authentication and authorisation**, with per-reviewer identity replacing the synthetic reviewer
- **Server-side, tamper-evident audit storage** — append-only, signed, retained
- **Temporal modelling** — trending observations, detecting deterioration from deltas rather than absolutes
- **Real FHIR ingestion** from a hospital server, with pagination, rate limiting and provenance
- **Much larger evaluation corpora**, including adversarial and out-of-distribution splits, with metrics reported per subgroup
- **Calibration analysis** — reliability diagrams, expected calibration error, per-label thresholds
- **Clinician-led annotation** of a labelled corpus, with inter-rater agreement
- **Prospective shadow deployment**, measuring agreement with human judgement before any influence on workflow
- **Regulatory work** — regulatory classification, quality management system, post-market surveillance
- **Security controls** — CSP, dependency scanning, secret management, penetration testing

## Interview discussion points

Questions this project is designed to provoke good answers about:

1. **The first model scored 10% accuracy.** What was actually wrong — the model, or the scoring
   function? (The scoring function. Raw cosine similarity differences were too narrow a band to
   discriminate; softmax over similarities fixed it.)
2. **The conventional ensemble performed worse than its own components.** Why? (Averaging lets a
   confidently-wrong engine drag a correct one down, and lets borderline records clear a threshold
   neither engine should have cleared.)
3. **What does "100% selective accuracy" actually mean?** (Accuracy on committed records, over 52
   synthetic scenarios. Coverage is the other half of the story, and the honest read is "no wrong
   answers in a small synthetic corpus".)
4. **How do you make a negation-aware rule engine?** (Clause-scoped, distance-limited, with
   contrastive connectors breaking scope — and how a trailing negation reaches back only one word,
   so "pain not reported" is a denial but "bleeding that did not stop" is not.)
5. **Why a browser model?** (PHI stays on device; ~30 ms warm; no inference server; deterministic
   scores that can be audited.)
6. **How do you know the system did not silently fall back to a less capable path?** (The original
   prototype did exactly that, and the UI claimed AI success. Every fallback is now explicitly
   labelled, and the fallback rate is a computed metric.)
7. **What would make you stop trusting it?** (Coverage that drops so low the workflow is useless;
   a single incorrect recommendation in shadow deployment; subgroup performance gaps; drift
   between the synthetic corpus and real documentation.)
8. **Why is there no LLM here?** (Three labels over structured-ish text do not need one, and the
   capability ceiling is not the binding constraint — privacy, latency, cost and determinism are.)
